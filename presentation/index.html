01 · Problem and solution

Practice investing, without risking a dollar

Where we started

  • The app ran on one laptop: data in a local file, API keys in a .env file.
  • Nobody else could use it, and if that laptop broke, everything was gone.
  • No tests ran automatically and no record of who changed what.

What we built

  • A public website where anyone signs up and gets $100,000 of simulated cash.
  • Real US stock prices, AI-labelled news, paper trades in stocks and options.
  • Runs on Google Cloud: always on, self-healing, deployed on every push.

02 · The website

One website, six things you can do

📈 Market

Search 4,000 US stocks, 90-day charts, a momentum rank and a plain-English explanation of each score.

GET /momentum

💼 Portfolio

Buy and sell by shares (fractions to 6 decimals) or by dollars ("$100 of AAPL"), with a live preview and profit/loss.

POST /portfolio/{id}/trade-stock

📰 Sentiment

Live market headlines, each labelled positive, negative or neutral by Claude and tagged with the stocks it mentions.

GET /news-sentiment

📊 Options

Calls and puts with a cost preview. Premiums are bounded by intrinsic value, so no one can sell an option for free money.

POST /portfolio/{id}/trade-option

🤖 Autopilot

Buys and sells by momentum rules, on a schedule during market hours or on demand, inside the user's risk limits.

POST /portfolio/{id}/autopilot/run

👤 Sign-in and profile

Email and password or Google sign-in, a profile photo, password change. Failed sign-ins are rate-limited.

POST /auth/login

Plus a Politicians view of stock trades disclosed by members of Congress (Quiver Quantitative). 9 pages and 51 API endpoints in total.

08 · Security

Security, layer by layer

🔒 In transit

  • HTTPS only; plain HTTP gets a 301 redirect
  • Database connections require TLS
  • Google-managed certificate, renewed automatically

🔑 Sign-in

  • Passwords hashed with scrypt and a random salt
  • One generic error message, so emails can't be guessed
  • 5 failures per email or 20 per IP in 15 min → 429

🗝️ Secrets and identity

  • Keys in Secret Manager; nobody has seen the DB passwords
  • GitHub deploys through Workload Identity: no key files anywhere
  • Each service account gets only the roles it needs; container runs as non-root

🗄️ Data

  • Cloud SQL has no public IP
  • Private bucket; a photo is only served to its owner
  • Photo type checked from the file's bytes, max 2 MB; prices from the server, never the browser
09 · Reliability

Built to stay up

19 s
a deleted pod was replaced and Ready
2 → 4 → 2
pods under load, then back down (HPA, 60% CPU)
668 / 668
requests OK while a node was drained

Why it heals itself

  • Readiness check (/ready) includes the database: a pod gets traffic only when it can serve.
  • Rolling updates with maxUnavailable: 0: old pods serve until new ones are ready.
  • Disruption budget kept 1 pod up during node drains.

Real incident: Nov 19, 4,000 stocks

  • The first 4,000-stock history download pushed CPU to 125%.
  • The HPA went to 4 pods and GKE added a 3rd node, with no errors.
  • CPU settled to 3%, and it scaled back down by itself.
10 · The pipeline

Every push to master goes live, or rolls back

1 · test

3 · deploy

kubectl set image, wait for the rollout

4 · check

Public URL: /health shows the new SHA, /ready is 200

11 · Monitoring

We know when something breaks

Logs

Every request writes one JSON line (path, status, duration) to Cloud Logging. No passwords or tokens in logs.

Metric and alert

Log-based metric app_http_5xx counts server errors. Above 0 in a minute → email alert; a "recovered" email when it clears.

Dashboard

5xx per minute, load-balancer requests by response class, CPU and memory per pod, container restarts, the alert's state.

Proof (Nov 8)

3 controlled 500 errors → the metric went 0 → 3 → incident opened → email arrived → closed after a quiet minute.

Budget alerts

Billing alerts at $10 / $25 / $50, so a runaway cost shows up early.
